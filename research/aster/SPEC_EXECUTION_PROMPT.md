## 0. Research target

Implement and evaluate the manuscript:

**ASTER: Authorization-Scoped Threshold Exact-Domain Credential Derivation with Failure-Safe Root-Epoch Healing**

The paper's core claims are:

1. Exact policy compliance and deterministic reconstruction.
2. Strict same-lineage non-repetition because generation is an input to one exact-domain permutation.
3. Normal endpoint operation never reconstructs or receives a Root-Epoch key or reusable per-lineage derivation key.
4. Every evaluation is authorized for exactly one canonical credential request unless a deliberately broader test capability is used.
5. A compromised old root is healed only by an independently generated new Root-Epoch plus successful relying-party credential migration; proactive resharing of the same root is a negative control, not healing.
6. Cross-epoch password-history exclusion occurs without storing historical password values.
7. Ambiguous remote password-change outcomes preserve both old and candidate reconstruction paths.
8. An old Root-Epoch cannot be retired while any committed, pending, unknown, or required-history state still depends on it.

Do not claim that Shamir, MPC, OPRF/POPRF, FF1/FPE, Rank/Unrank, cycle walking, capabilities, or generic two-phase commit are new primitives.

## 6. Threshold/MPC backend

### 6.1 Goal

Implement a real **2-of-3** threshold/MPC research backend and a **3-of-5** comparison backend such that the endpoint never reconstructs the Root-Epoch key or a reusable per-context permutation key.

### 6.2 Preferred implementation path

Use **MP-SPDZ** unless repository/platform constraints make another mature actively secure MPC framework materially better. If using another framework, document why.

The backend interface must remain abstract:

```text
create_root_epoch(epoch) -> public epoch metadata
refresh_shares(epoch) -> same root, new sharing state
retire_epoch(epoch)
eval_exact_rank(request, capability, N_P) -> rank
derive_password(request, capability, compiled_policy) -> password
select_migration_candidate(request, capability, history_descriptors, compiled_policy) -> candidate_generation + password
```

### 6.3 Exact-domain permutation

Do **not** invent an unreviewed “threshold FF1” and claim standard security.

Implement one defensible research route:

**Primary route:** secure MPC evaluation of an established keyed permutation over a superset domain, with cycle walking into `[0,N_P)`, using established FPE/arbitrary-domain methodology. The permutation key remains secret shared. All conditionals that would reveal secret intermediate values must be handled inside MPC.

Requirements:

- generation is the permutation input;
- full canonical context and Root-Epoch domain-separate the key/tweak;
- no modulo reduction fallback;
- explicit minimum/maximum supported domain;
- explicit cycle-walk cap with fail-closed behavior if needed;
- record cycle-walk count distribution as an implementation metric;
- document timing/leakage assumptions;
- compare outputs against the local semantic backend on fixed test vectors where both are defined.

If MP-SPDZ lacks a clean implementation primitive, first create a correct generic-MPC version and then optimize. Correctness and scope separation matter more than speed.

### 6.4 DKG / independent Root-Epoch replacement

Implement independent Root-Epoch creation. The new epoch secret must not be deterministically derived from the old root.

Also implement `refresh_shares(epoch)` as a **separate** operation that preserves the same root. This will be used as the negative control demonstrating that share refresh does not heal complete root disclosure.

If the selected MPC framework does not provide a production-grade dealerless DKG, the research prototype may use an explicit trusted setup script to create a random root and secret-share it among parties, but:

- document this limitation;
- do not call it dealerless DKG;
- keep the root off the endpoint;
- make Root-Epoch replacement independently random;
- preserve an upgrade path to DKG.
