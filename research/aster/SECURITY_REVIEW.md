# ASTER adversarial implementation review

1. **Endpoint material before/during/after use.** Before use the endpoint holds public metadata only. During a legitimate response it holds the capability and plaintext output. After best-effort clearing it retains neither. The public API exposes no Root-Epoch key, evaluator share, or reusable lineage key. This is a structural claim, not whole-process memory forensics.
2. **Capability amplification.** Exact mode binds every canonical field. Mutation and universe tests cover service, account, lineage, policy hash/epoch, Root-Epoch, generation, freshness, expiry, revocation, and nonce budget. Projected/wildcard modes intentionally demonstrate amplification.
3. **Recovery collapse.** Normal evaluator APIs do not expose recovery shares or a root-reconstruction operation. Operational separation of recovery trustees is still required and is outside the current executable artifact.
4. **Divergent evaluator validation.** The semantic interface centralizes one validator. The MP-SPDZ experiment addresses only exact-domain circuit feasibility and assumes the authorized request has already been admitted. A production evaluator must validate the same signed request independently at every party before contributing to the computation.
5. **Root/reusable key at endpoint.** No endpoint-facing return type contains either. The semantic evaluator process does contain the root. In the MP-SPDZ circuit, parties input private contributions and XOR them only inside MPC; the reported fixed-vector experiment does not prove whole-process erasure or DKG security.
6. **Share refresh.** Code, tests, and results label it a negative control: output families remain unchanged after refresh.
7. **Stale snapshots.** Freshness and Root-Epoch fields are signed and independently checked. The fault matrix rejects stale capabilities before submission; a production monotonic anchor remains an operational dependency.
8. **Unsafe erasure.** Committed, pending, unknown, candidate, and required-history descriptors contribute to the referenced-epoch set. Retirement is refused while any reference remains.
9. **HTTP success.** HTTP 200 is transport evidence only. The local target includes a 200-without-commit case, and the journal commits only after `new_only` adapter evidence.
10. **Password persistence.** ASTER journals and result schemas contain descriptors, evidence, counts, and redacted secret types only. Adapter targets persist verifier hashes because they model relying parties. Repository scans must exclude target verifier databases and still reject password-bearing ASTER result fields.
11. **Directory interoperability.** The pinned single-server OpenLDAP smoke verifies modify/bind behavior only. It does not establish replication consistency, failover safety, directory hardening, or production performance.
